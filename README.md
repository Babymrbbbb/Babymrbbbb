# 用 AI 重构门店运营落地模式

我是 47 家烘焙连锁门店的**用户运营负责人**。我把运营里每天重复发生的劳动，一件一件改造成由 AI 驱动的自动化运营分析——现在这套东西每天在公司里真实运行，不是演示。

**[→ 读完整落地复盘](https://Babymrbbbb.github.io/article.html)**（背景、数据、分析、成果、AI 边界与 Agent 搭建）

> 清远含连州 40 家 / 广州含花都 4 家 / 肇庆 2 家 / 佛山 1 家 · 服务约 20 万终端客户

---

## 一、我面对的是什么

47 家门店意味着每天几十份数据要汇总、几十个问题要回答、几十条动作要追踪。真实的困难不在策略，在执行密度——六个卡点，全都指向同一个问题：分析和执行之间没有闭环。

| 卡点 | 具体表现 |
|---|---|
| **数据散** | 订单、会员、客流分散在不同系统，每天手工汇总，口径还不统一。同一家店的营业额，三个系统能给出三个数 |
| **知识散** | SOP、新品资料、加盟政策散落在文档里。店长查得慢，新人靠口口相传，同一个问题不同人答出不同答案 |
| **情报散** | 竞品动态无人持续整理，等到要做决策时找不到 |
| **重复劳动多** | 话术、日报、作战卡、复盘，每天重复做同样的事 |
| **数据分析浅** | 能拉出数字，但看不出原因：哪家店为什么掉、掉在哪个品类、该动哪个动作，全靠人一个个翻 |
| **落地执行断** | 分析结论停在报告里，到店长手上就变成「知道了」。谁做、什么时候做、做完没做，无人追踪 |

前四个是「量」的问题，靠工具和自动化能解决。后两个是「质」的问题——分析出来的结论没有变成门店当天要做的动作，动作做完也没有回到数据里验证。

所以这件事从一开始就不是「上一个 AI 工具」，而是**重做一遍运营的落地方式**。

## 三、我用 AI 做了什么

四个阶段，每个阶段都对应一个真实发生过的故障——不是先有技术再找场景。

### 阶段一 · 接入：让 AI 调用稳定下来

**故障**：多个模型账号配额不够，429 频繁中断，AI 一忙就不可用。

**做法**：自建本地模型网关，把多个账号聚合成一个端点，按配额自动轮询，遇到限流或失效自动切换并隔离。

**结果**：上层所有 AI 应用有了稳定底座，不再因为单个账号限流而停摆。

### 阶段二 · 用好：让 AI 产出可用

**故障**：AI 出的图、出的视频一眼就假，内容生产变成碰运气。

**做法**：把每次成功的写法沉淀成方法论——通用铁律、图像结构、视频叙事骨架，全部经过实测验证后入库。

**结果**：AI 内容产出一遍过的比例明显提高，方法可复用给团队。

### 阶段三 · 知识：让答案带出处

**故障**：文档越攒越多却找不到，知识是死数据；直接问大模型会编造，因为它不知道我的业务事实。

**做法**：搭一套知识库系统——模型把原始资料编译成可导航聚合页，检索精确召回，命中页作为上下文再交给模型生成带引用的答案。

**结果**：1,600 余篇原始资料编译成 1,300 余个可导航页面，问答可追溯来源。

### 阶段四 · 组织与交付：让 AI 真的进入业务流程

**故障**：AI 能力很多，但组织消化不了，工具之间互相覆盖，最后没人用。

**做法**：一边把多个 AI 角色编排成有分工、有决策边界、有校验闸门的生产线；一边把高频操作做成两套 Windows 桌面软件——经营驾驶舱和调度运维工作台。

**结果**：AI 从「偶尔试试」变成「每天打开的生产工具」。

## 四、知识库具体怎么搭的

这一节单独讲，因为它是整套系统里最难、也最容易被误解的部分。它不是「把文档丢给模型」，而是重做了一遍知识的组织方式。

**问题出在哪**：原始文档和模型答案之间少了两层——一层负责把散落的资料组织成可导航的结构，一层负责在提问时精确召回。缺了这两层，模型只能靠印象答，也就是编造。

| 层 | 作用 | 规模 |
|---|---|---|
| **原始语料** | SOP、新品资料、竞品分析、加盟政策、决策记录，按 11 个子库分域存放 | 1,600+ 篇 |
| **聚合编译层** | 模型把多源资料按「实体 / 概念」重新编译成聚合页，每页带摘要、关键事实、来源列表 | 1,300+ 页 |
| **三层索引** | 倒排索引管精确术语、向量索引管语义换说法、聚合索引管跨源关联，三路召回后融合排序 | 三路并行 |
| **带引用生成** | 命中页作为上下文交给模型生成答案，强制标注出处；追溯不到来源就直接拒答 | 可追溯 |

**搭完之后得到的三个结论**（不是事先设计的目标，是实际验证出来的）：

1. **评测必须固化成用例**——24 条用例覆盖 11 类场景，每次改检索链路必须全量回归。没有这条，改一处坏三处，你永远不会知道。
2. **事实只能有唯一真相源**——门店数曾因「旧文档 77 篇 vs 裁决 1 篇」，朴素检索让旧口径获胜。关键事实必须单一来源，冲突时以裁决为准。
3. **测试绿不等于线上对**——曾出现「索引重建了但内容读不出」，问答上下文全靠聚合层在撑。验证正确性必须做检索探针。

## 五、我沉淀的方法论

这些不是技术，是踩过坑之后提炼的判断规则。每一条都对应一次真实的翻车。

### 多轨交付终核法（A-88）

**问题**：多个自动化任务同日产出，声称都交付了，但实际有假交付漏网。只查「有没有文件」不够。

**四查**：查落盘（草稿不计件）、查档位（应 N 档实 M 档即退回）、查占位符（≥3 次判空壳）、查口径（必须标数据日期与来源）。

### 「名义增量、实际无增量」判定法（A-94）

**问题**：数据管道的时间戳推进了，看起来是新数据，但实际数据还停在昨天。看时间戳会得出错误结论。

**四步**：查元信息 → 验模块实际日期 → 判形态（名义增量 / 空壳半成品）→ 全量重核，结论时效以实际数据日为准。

### 分析结论三道自检

**问题**：AI 最容易出的错不是算错，而是给了一个听起来对、但站不住的结论。

**三防**：防假环比（基线同口径）、防假异常（区分噪声）、防不可信归因（落到可验证因素）。

### AI 边界四层

**问题**：靠自觉守边界迟早会破。边界必须做成系统约束，它才真的存在。

**四层**：数据边界（分层授权）、动作边界（不能直接执行）、表达边界（必须标来源）、失败边界（不确定就说不确定）。

## 六、哪些决策必须我自己拍板

AI 可以替我做「分析和执行」，但不能替我做「判断和责任」。

| 决策类型 | 谁来决定 | 举例 |
|---|---|---|
| **事实类**（AI 决定） | AI 决定，我抽检 | 昨天哪家店环比下降、降了多少、哪个品类降得最多。有明确数据源，AI 比人快也更不容易漏 |
| **建议类**（我拍板） | AI 出选项，我拍板 | 这家店要不要做促销、做多大力度、推哪个品。涉及成本和品牌调性，选哪个由我定 |
| **责任类**（只能我定） | 只能我决定 | 是否关店、是否换店长、是否调整加盟政策、是否对外承诺。一旦错了就是真金白银和人心 |

> AI 算得出坪效，算不出这家店背后的人、算不出关店对周边门店口碑的影响、算不出加盟商的感受。**AI 不会为结果负责，我会。**

## 七、Agent 怎么搭

我没有一上来就做「全能 Agent」，而是一个个拆。全能 Agent 的问题是：出错时你不知道错在哪一环。

| 角色 | 职责 | 输出 |
|---|---|---|
| **数据角色** | 拉取、清洗、对齐口径 | 结构化当日经营数据 |
| **分析角色** | 跑三道自检、做归因 | 通过自检的结论 + 异常门店清单 |
| **知识角色** | 回答「标准是什么」 | 带出处的 SOP / 政策答案 |
| **生成角色** | 把结论变成门店能执行的话 | 作战卡、话术、简报 |
| **追踪角色** | 记录动作是否执行、结果如何 | 执行台账 + 回流数据 |

角色之间靠固定格式传递，不靠自由对话——哪一环出错，看输出就知道；要改也只改那一环。

**为什么不让 Agent 自己决定顺序**：运营有硬时序。数据没拉完不能分析，分析没过自检不能下动作，动作没执行不能复盘。这些顺序是业务规律，不是 AI 该自由发挥的地方。所以顺序写死在流程里，AI 只在每一步内部做判断。

再往上一层是调度：我下指令，系统判断该叫哪几个角色、按什么顺序跑。44 条自动化任务就是这一层的产物。
